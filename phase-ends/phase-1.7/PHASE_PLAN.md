## Rationale
- Shape: a first-wave phase, not the whole campaign. The mechanical conversion already exists (listing self-check 246/246); what is missing is (1) the default build from instruction source, (2) verdicts for the 6 inferred code rows, (3) readability (names, comments), which is the long tail. The milestone's "0 undecoded" is reachable this phase; naming and commenting of all 246 regions is not, and continues as waves under 1.9 Readability (already scoped "names, comments and constants complete"). No milestone text change is needed; proposed generation-plan note below (Risks: no `plan_edit.py` verb edits a milestone or scope).
- Where source lives is the developer's (D1). T1, T2, T5, T6 are independent of it; T4 (source pipeline) and T7 (wave, which writes comments and names into whatever the source is) wait for T3, the decision record. Recommendation (a) is chosen as the default the other tasks are drafted against because it is the only option that is reversible: a sidecar-rendered source can be emitted into a tracked `src/` later in one commit if the developer ever supersedes G12 for publication, while (b) cannot be undone without a history rewrite.
- Options for D1 (evidence in Context): (a) private working tree / rebuild-from-dump: instruction source is generated (`db.py listing` + names + comments sidecars) into ignored `asm/src/`; readability lives in tracked sidecars keyed by address (`config/names/*.tsv`, `config/ghidra/comments.tsv`, later an operand-expression sidecar for constants); full G12 compliance, publish gate (1.8) is a contract run; cost: hand edits to source text are impossible (H1), every readability construct needs a sidecar renderer, readers need their own dump to see code. (b) track `src/` in this private repo with a dated exemption: violates G12 exactly as written (no private exemption); requires relaxing `asm_leak` and the purge set; publishing later needs the DK-53..56 rewrite with host purge or a recreated repo, or never publishing source. (c) hybrid: source in a separate never-published private repository (this repo stays compliant; two repos to sync; build points at an external path) or an encrypted archive in git (ciphertext of game code is still game-derived bytes in git and needs key management: rejected as worse than both). The question underneath (does the published project ever ship assembly source, as community Mega Drive disassemblies do) is legal risk appetite and product intent: a project rule superseding G12 at a named commit, not a private exemption, if ever.
- T1 first: the ledger and the measurements (per-region instruction count, raw address operands, labels, embedded `dc.b` bytes, comments, listing time) are needed by every later task and by D1 (how much of readability is sidecar-expressible), touch no source and decide nothing.
- Unit of conversion = one verified code region (ledger row); a region is "banked" when it is built from instruction source with closeness 0 (no raw absolute operand that has a nameable target left unnamed, every routine entry named or neutrally placeholdered, every embedded data run classed) and the byte gate holds.
- Manual wave size 6, stratified 2/2/2 by instruction count (< 50, 50-300, > 300; mean 156 insns/region = 38504/246), picked from regions executed in `config/oracle/coverage.tsv` and preferring signature-group members (propagation multiplier, G7). Evidence: 1.6/T4 named one 7-member group plus two structs in one expert context; 6 regions across three strata is the smallest batch that measures a rate per stratum (DK-43: measure the routing cliff, never hand-wave it) inside one task. Gate after each region (`make build`) and after the wave (`make health`).
- Routing (T8 writes it into the ledger from T7's numbers): unattended = mechanical classes (neutral placeholders, propagation of an already named group, embedded-data classing, structural labels); developer review = any meaning-bearing name or comment (G62: a model proposes, a person with evidence asserts; >= 3 datapoints rule). T7 is `review: yes` for that reason.
- Census assertion: `ledger.py check` (T1 tool, T8 wires it as health rung `ledger`) counts a code row undecoded if it is absent from `asm/.srclist` after the default build, or inferred without a recorded verdict. Embedded `dc.b` runs inside code listings are counted and classed on the ledger, not part of the 0 (they are data by Ghidra's verdict; T1 measures how many).
- T5 is `effort: high` (expert-fable; not installed on this tier, runs on expert-opus55): the verdict for each inferred row is a proof read from evidence (emulator taps, references, decode validity) that no test arbitrates. 1 of 8 tasks. The hard rung exists on this preset (`max20`); no other task rests on such a judgment: T3's judgment is the developer's, T7's names are arbitrated by the developer at review.
- T2 (decrunch re-key) is small but kept separate: it touches extraction readers and the manifest check, a different failure surface from the campaign, and removes a manual step every region insert in T5 would otherwise need. It runs before T5.
- T6 before T7 so the wave can use value datapoints for meaning names. Scenarios are re-created as tracked probes under `scripts/oracle/lua/` (the `.run/t4/` scripts are scratch and may be gone).
- Coder tier: opus55 everywhere (single tier). T3 has `coder: none` (a decision record and one doc edit). All experts 1h TTL (`expert_ttl.py` prints 1h for both).
- Rejected: converting regions "routine by routine" by hand (the listing already converts mechanically; hand conversion adds risk, no value); a new health pair per follow-up (only the ledger rung is added; decrunch keyed by name is covered by `manifest.py --check`).

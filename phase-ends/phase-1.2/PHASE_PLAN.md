## Rationale
- No MCP bridge this phase. Ghidra MCP servers need a running GUI/server the agent cannot start or reconnect (G2's "ask the developer to reconnect"), which stalls an autonomous phase. `analyzeHeadless` and MAME `-video none` with a Lua autoboot script are agent-runnable, deterministic, loggable through `tools/run.sh`. G2's precondition becomes a scripted cheap probe (`db.py probe`, `mame.py probe`) every later task runs first. Revisit an MCP only if phase 1.7 campaign tasks show per-query headless cost dominating (measure there; the ops doc records this).
- MAME is the primary runtime oracle: true headless, Lua debugger API, J-Cart device in its megadriv cart slot. BizHawk (Genesis Plus GX) is the G21 second, disagreeing oracle, but it is a GUI app; launching it needs the developer's consent (Developer decides 1). Without it, the second path for each claim is the static oracle (Ghidra xrefs) plus a controlled before/after in MAME.
- Decoded-row promotion by harness call, not by waiting for the game to load all 368 assets: T3 drives the game's own decruncher 0x035416 inside MAME for every blob (set registers per its calling convention read from Ghidra, run to return, sha1 the destination) and compares with the offline `decode_imp.py` sha1. That is a controlled before/after per row (G5), 368/368 by the game's code, which is the 1.1 promotion contract (ops:21). >= 3 natural in-game calls confirm the calling convention and the harness is first run on a known-true case (G32).
- Entry promotion: three cold boots each tracing the first executed PCs after reset (expect PC 0 trap -> vector 0x10 -> 0x000200) plus the soft-reset path; evidence lands in `config/maps/rom.tsv` and a new `code` row `init` in `config/regions.retail.tsv` (`verified`, evidence citing the oracle run id).
- Claims live in two hand-edited TSVs, `config/maps/rom.tsv` and `config/maps/ram.tsv`, one claim per row with its datapoint run ids; raw observations are generated into `config/oracle/*.tsv` (addresses, ids, sha1s, counts; no bytes) by the oracle scripts. `check_maps.py` is one checker with modes: `--live` re-runs each claim's probe and requires >= 3 consistent datapoints; `--manifest` asserts promotion state. One checker, not one per task (proportionality).
- Segmentation (T4) uses two independent signals: Ghidra auto-analysis + xref recovery (static) and a MAME PC-coverage trace over boot, attract and a scripted race (runtime). A region becomes `code` when executed or reachable by a resolved xref, `data` when referenced only as data; disagreement between the two goes to a residue list, not a guess. Exhaustive runtime coverage is not required; static reachability carries unexecuted code.
- Task split: Ghidra (T1) and MAME (T2) are independent and can run in either order; T3 and T4 need both; T5 closes maps and docs. Five tasks, sequenced; T1 and T2 have no deps on each other.
- effort: high on T2 only (1 in 5). The judgment: whether the emulator oracle observes what it claims (right driver/cart slot with J-Cart, that a Lua hook fires on the instruction it names, that a trace of PC 0 -> 0x000200 is real and not an emulator HLE shortcut) is a harness probe no test arbitrates. expert-fable is not installed on this tier, so it runs on expert-opus55 (1.1 harness note); the mark records the class of judgment.
- coder tier: opus55 for all (one tier). est-ctx sized for one expert context each.

- Ghidra export non-determinism (auto names, analysis order, float formatting) breaks the round trip. Detection: `roundtrip` itself; mitigation: export only owned annotations, sorted.

- Coverage-driven segmentation leaves a large unreached residue (menus, editor, J-Cart 4-player paths), stalling `verified` on many code rows. Detection: T4 residue counts; the milestone requires no `unknown` rows, not all `verified`.
- Long oracle runs exceed the 285 s tool-call cap. Detection: run timings in T2; mitigation `tools/run.sh --bg`/`--wait`.

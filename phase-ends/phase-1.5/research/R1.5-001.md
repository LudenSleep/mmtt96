## Answer
Recommend Capstone (pip `capstone==5.0.9`, M68K_000) for 68000. Independent of SLEIGH (Musashi-derived decoder). Capstone has no Z80 support (not in its arch list; unverified-absence). For Z80 use `z80dis==1.0.6` (pure Python, ~8 KB). Rizin/radare2 m68k is Capstone-backed, so NOT independent of Capstone. If a third, non-Capstone opinion is wanted: vda68k (C, compile yourself) or Musashi-derived code.

## Findings
- capstone 5.0.9: released 2026-05-28 (latest stable on PyPI), BSD, requires_python >=3.8, win_amd64 wheel `capstone-5.0.9-py3-none-win_amd64.whl` = 1,273,459 B (~1.2 MiB), sdist 2.9 MB. Pip: `pip install capstone==5.0.9`. Source https://github.com/capstone-engine/capstone
- capstone 6.0.0a11 (pre-release, 2026-09-21; `pip install --pre`): cp38-abi3 win_amd64 wheel 2,496,443 B. 6.x is still alpha series (a1 2024-09 to a11). Prefer 5.0.9 for stability. NB: CVE-2026-49282 (OOB read in cs_insn_name for M68K/RISCV with untrusted ids) is fixed in 6.0.0a9; irrelevant if you only decode real ROM bytes and never pass arbitrary ids to cs_insn_name.
- Strictness: Capstone M68K modes M68K_000/010/020/040 plus ColdFire. In M68KDisassembler.c, `features = handle->mode & FEATURE_MASK; if (!features) features = CS_MODE_M68K_000`. 68020 handlers (bfchg/bfextu/bfins etc., cas/cas2, chk2/cmp2, divl/mull, extb) call `LIMIT_FEATURE(info, M68020_PLUS...)`, so in 000 mode they should be rejected as invalid (macro body/table not read; VERIFY EMPIRICALLY with a test: encode bfextu `E9C0 ...`, `extb.l` 49C0 and expect decode failure in M68K_000). That LIMIT_FEATURE path is read from the `next` branch (6.x line); 5.0.9 may differ slightly.
- Known bugs: found no GitHub-issue evidence of movem/bitfield length bugs (search index weak; NOT FOUND is not proof). Capstone m68k is heavily modified from Musashi's disassembler; operand syntax differs from Motorola/vasm style, so compare lengths/mnemonic class/targets, not text. Deterministic (pure table decode, no state besides address). Use disasm_lite or full detail for branch targets (operand imm or PC-relative already resolved to absolute in m68k operands; check br_disp fields).
- Capstone Z80: not supported (README arch list: ARM, ARM64, Alpha, BPF, EVM, HPPA, LoongArch, M68K, M680X, MIPS, MOS65XX, PPC, RISC-V, SH, Sparc, SystemZ, TMS320C64X, TriCore, WASM, X86, XCore, ...). Confirmed no Z80.
- rizin/radare2: rz-asm table lists m68k as "Capstone M68K disassembler", BSD, d+A flags only. Therefore not independent of Capstone. Windows builds are tens of MB. Not recommended. radare2 also has a GNU-binutils-based `m68k.gnu` plugin in some builds (NOT verified; check `r2 -a m68k.gnu`) which would be an independent decoder but accepts 68020+.
- vda68k (Frank Wille, same author as vasm/vbcc): plain C, easy to compile, Aminet dev/asm/vda68k (http://aminet.net/package/dev/asm/vda68k), distributed as .lha (7-Zip extracts). No official Windows binary found; needs gcc/MSVC. Version/date/license not retrieved (Wille's vdappc is "freeware, noncommercial, keep copyright"; vda68k likely similar, verify in readme). Handles 68000-68060 so not strict. Fully independent of Ghidra and Capstone code (Musashi-lineage not involved).
- Musashi m68kdasm.c (kstenerud/Musashi, MIT-style): C, requires compiling; no pip package for the disassembler alone. `machine68k`/`bare68k` on PyPI are Musashi EMULATORS (Cython, need C compiler on Windows), not disassemblers; machine68k wraps Musashi so could be abused but not a disassembler API (verify).
- m68kdis: NOT FOUND as a maintained tool. Pure-Python 68000 disassemblers on PyPI: NOT FOUND (only easier68k assembler/simulator, bare68k, machine68k).
- Z80: `z80dis` 1.0.6, 2020-05-01 (stale but stable, ISA fixed), public domain classifier, wheel 7,912 B, sdist 6,961 B, https://github.com/lwerdna/z80dis, `pip install z80dis==1.0.6`; API disasm() and decode() with length. Alternative `yad80` (CLI, follows control flow, emits reassemblable source), not evaluated for size. Z80 on Mega Drive is only the sound CPU, so tiny scope.

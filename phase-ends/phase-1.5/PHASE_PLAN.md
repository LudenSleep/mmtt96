## Rationale
- Second oracle = Capstone 5.0.9 (R pending web report): decoder derived from Musashi, independent of Ghidra SLEIGH; 1.2 MiB win_amd64 wheel; BSD; deterministic table decode; `CS_MODE_M68K_000`. Rejected: rizin/radare2 (m68k backend is Capstone, so no extra independence, large install); vda68k and Musashi m68kdasm (need a C toolchain, no Windows binary; vda68k is a fine third opinion later); Capstone 6.x (alpha). Fallback if the developer refuses the install: an own stdlib 68000 length decoder in Python (opcode + EA-mode size table, ~400 lines) — independent but itself a new instrument, so T1 then grows a known-true battery first; T1 keeps the oracle behind one function (`decode(rom, addr) -> (length, mnemonic, targets)`) so either backend plugs in.
- Z80 driver (2 rows) stays out of the boundary diff: Ghidra holds no Z80 disassembly to compare against (rows are data-form), so a second Z80 decoder has no first oracle. No `z80dis` install this phase; revisit in 1.6/1.7 when the driver is converted.
- Ghidra side reuses the listing TSV (`Mmtt96Listing.java:68`): one headless batch over all verified code ids; no new Java, no db edits.
- Comparison unit = instruction boundaries (primary, milestone), mnemonic class and absolute branch/jump targets (secondary, reported, each disagreement classed). Linear sweep inside each region is correct for verified code: every verified row self-checks as pure instructions under Ghidra. Phantom = boundary in one stream only; truncation = a stream that stops early or overruns the region end. Explained disagreements need a tracked row in `config/oracle/boundary_exceptions.tsv` (`region_id class reason`, ids only); none expected for boundaries.
- Census: one stdlib script, ROM read from the ignored dump at runtime, tracked nothing instruction-level. Duplication = equal content hash across regions (the manifest already tracks sha1 per id, so grouping ids by it adds no new game-derived fact to `.run` output); structural family = equal Capstone mnemonic-skeleton hash (operands stripped) across code regions; reach = inbound refs per region (seed refs) x size bucket; unique tail = code regions with no duplicate and no family sibling. Each metric gets a known-true case (G32, DK-61): a synthetic fixture under `.run/` with planted duplicates/families/refs and known answers, run before the real census.
- Progress/difficulty report: denominators from `make build` products (`build/mmtt96.bin` size), regions TSV and manifest; asserts the regions partition [0, ROM size) with no gap/overlap and that manifest region records equal TSV rows (G19, G27, G58). Numerator = code bytes whose `asm/src/<id>.asm` assembles in the build. Never a typed number.
- Differential pairs (DK-9), at least five, in `make health`: (1) boundaries Ghidra vs Capstone; (2) instruction-form build (all verified code from `asm/src`) vs all-data `SRC=` build, both hash OK; (3) incremental vs clean build hash; (4) census partition count vs manifest/over-approximating set (scanner coverage); (5) `config/regions.retail.tsv` vs `config/ghidra/regions.tsv` mirror agree row for row; (6) `coverage.py --check` executed PCs vs code rows; (7) `check_maps.py` MAME vs BizHawk datapoints (offline), with `--live` as a separate detached rung `make health-live` (P1.2-1). Plus a firewall rung (AS-style listing scan of `git ls-files`), not counted as a pair. Each pair gets one planted-failure control proving it fires (G25, C0008).
- Schedule: the health chain is the gate of every phase close from 1.5 (binding decision written by T5) and is run by the closing expert; an OS scheduler is a developer call (Developer decides 2).
- Split: T1 instrument (install + boundary diff), T2 census + progress, T3 health chain, T4 findings, T5 docs + milestone. T2 and T4 depend on T1's decoder; T3 wires T1/T2 tools as rungs. Small and sequenced; no parallel batch (shared `.run/ghidra/` and build tree).
